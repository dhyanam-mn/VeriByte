# 1. Introduction

Modern software deployment relies heavily on platform-independent bytecode architectures. Compiling source code into an intermediate bytecode distributed to a client-side or in-kernel virtual machine (VM) decouples language implementations from hardware targets while theoretically establishing a sandboxed isolation boundary. Representative architectures span the Java Virtual Machine (JVM) [@lindholm2014java], the Common Language Runtime (CLR) [@meijer2002technical], browser-embedded WebAssembly engines [@haas2017bringing], and kernel-space eBPF execution engines [@ebpf2023linux].

In standard compiler curricula and baseline runtime engines, compiler design ends at syntax-directed code generation, leaving the execution engine to implicitly trust the generated bytecode. In adversarial environments, this implicit trust model fails catastrophically. A binary executable can be hand-crafted in binary hex editors, emitted by compromised third-party compilers, or corrupted during network transit. When an untrusted bytecode binary containing invalid control-flow targets or mismatched stack operands enters a native VM loop, it triggers:

1. **Stack Underflow and Overflow:** Popping from an empty evaluation stack reads adjacent host memory; pushing beyond capacity corrupts activation frames.
2. **Control-Flow Hijacking:** Jump targets pointing into the middle of multi-byte instruction encodings cause data operands to be decoded as opcodes, leading to arbitrary code execution.
3. **Type Confusion:** Arithmetic instructions executing against boolean flags or object references bypass high-level type safety invariants.
4. **Uninitialized Local Access:** Reading unassigned local variable slots leaks unscrubbed host memory registers.

To counter these vulnerabilities without paying the steep runtime performance penalty of defensive interpreter traps (which require checking stack pointers and dynamic types at every fetch-decode-execute step), modern architectures enforce static bytecode verification prior to program instantiation.

In this work, we present **VeriByte**, a complete, fully verifiable stack-based compilation and execution pipeline designed as a trust boundary. VeriByte implements an imperative source language (*MiniLang*), a two-pass semantic type analyzer, a 27-opcode stack-based binary bytecode generator, a bytecode optimizer with constant folding and jump threading, a static bytecode verifier employing Kildall's worklist abstract interpretation algorithm [@kildall1973unified], and a high-performance virtual machine interpreter equipped with a checked-mode verification oracle.

The primary contributions of this paper are:
- **System Architecture as a Security Boundary:** We establish an end-to-end verifiable pipeline enforcing the principle that no untrusted bytecode is ever admitted to the runtime interpreter without preceding inductive safety verification.
- **Thirteen Formalized Safety Rules:** We formalize and implement thirteen static safety invariants spanning bytecode structure, control-flow graphs (CFGs), operand-type lattices, join-point stack unification, and call/return typing.
- **Attack-and-Defence Corpus:** We validate verifier precision against a handcrafted corpus of 26 exploit binaries designed to isolate each rule violation, juxtaposing unverified execution crashes against clean verifier rejections.
- **Checked Soundness Oracle and Differential Fuzzing:** We evaluate verifier soundness via a 15,000-mutant structural fuzzing campaign and a 10,000-mutant raw-byte serializer fuzzing campaign. We validate the fuzzer's sensitivity through an intentional verifier weakening meta-test.
- **Empirical Performance Profiling:** We demonstrate that verification scales linearly ($\approx 180\text{ KB/s}$) with an execution overhead under 0.5%, confirming the practical viability of load-time verification.

# 2. Literature Survey

The theoretical foundations of static bytecode verification originate in abstract interpretation, type systems, and monotone dataflow frameworks.

## 2.1 JVM Bytecode Verification and Stack Maps
Early iterations of the Java Virtual Machine Specification [@lindholm2014java] implemented dataflow-based type inference to reconstruct operand stack shapes at runtime. In seminal work, Leroy [@leroy2003java] formalized Java bytecode verification using abstract interpretation over an abstract machine, establishing proof obligations for type safety and progress-preservation properties. However, because multi-path type inference exhibits polynomial computational complexity, Sun Microsystems introduced the `StackMapTable` attribute in Java ME and Java 6+. Rather than inferring types from scratch, the modern JVM validator verifies pre-computed type annotations in linear time. VeriByte deliberately adopts the more academically rich full-inference abstract interpretation approach, solving the fixpoint over loop back-edges without requiring external compiler-assisted stack maps.

## 2.2 WebAssembly Validation
WebAssembly (Wasm) was designed specifically to provide memory-safe, near-native execution inside web browsers [@haas2017bringing]. Unlike arbitrary stack machines, Wasm enforces structured control flow (avoiding arbitrary goto/jump instructions). This enables single-pass linear validation where operand stacks are validated syntactically using typed block signatures. While structured control flow simplifies validation, legacy and low-level architectures rely on unstructured jump primitives. VeriByte tackles the more generalized, unstructured control-flow domain where jumps can target arbitrary byte offsets, necessitating explicit CFG decoding and merge reconciliation.

## 2.3 Linux Kernel eBPF Verification
Extended Berkeley Packet Filters (eBPF) permit user-space applications to execute sandboxed code inside the Linux kernel [@ebpf2023linux; @gershuni2019simple]. Because kernel panics are unacceptable, the kernel's in-tree verifier performs symbolic execution to simulate all possible execution paths, validating that registers contain safe data types, pointer arithmetic stays within allocated buffer boundaries, and programs terminate within bounded instruction limits. VeriByte adopts a comparable threat model: untrusted binaries submitted from external sources must pass static analysis before admission to the runtime.

## 2.4 Abstract Interpretation Foundations
Cousot and Cousot [@cousot1977abstract] established abstract interpretation as a unified lattice model for approximating the semantics of programming languages. In VeriByte, the concrete execution domain (holding 32-bit integer values and boolean bits) is abstracted into a finite type lattice ($\mathbb{L} = \{\bot, \text{int}, \text{bool}, \top\}$), augmented with definite assignment tracking states ($\{\text{UNSET}, \text{CONFLICT}\}$). Monotonicity over this bounded-height lattice guarantees convergence to a fixed point.

# 3. Methodology and Architecture

## 3.1 System Architecture
The VeriByte toolchain is organized into modular phases forming an end-to-end compiler and verification boundary:

```
[Source .ml] -> [Lexer & Parser] -> [AST] -> [Semantic Analyzer]
                                                     │
                                                     ▼
                                            [Bytecode Generator]
                                                     │
                                                     ▼
                                            [Bytecode Optimizer]
                                                     │
                                                     ▼
[Untrusted Bytecode .bc] ────────────────> [STATIC VERIFIER]
                                              │           │
                                         Pass │           │ Fail
                                              ▼           ▼
                                          [Bytecode VM] [Diagnostic Reject]
```

The toolchain operates across two primary pipelines:
1. **Source Compilation Pipeline:** Source files (`.ml`) pass through lexical analysis, recursive-descent parsing with precedence climbing, two-pass semantic type analysis, stack bytecode generation, and optional optimization before entering the verifier and VM.
2. **Bytecode Admission Pipeline:** Externally supplied or precompiled bytecode files (`.bc`) enter directly at the serializer loader. The loader decodes header tables and immediately invokes the static verifier. Only bytecode certified as safe is permitted to initialize the virtual machine execution frames.

## 3.2 Source Language: MiniLang
MiniLang is a strongly typed imperative language supporting 32-bit signed integers and booleans. Its syntax includes variable declarations (`let`), lexical block scopes, conditional branches (`if` / `else if` / `else`), iterative loops (`while`), first-class function declarations with explicit signatures, return statements, and console printing (`print`).

The semantic analyzer enforces:
- Lexical scope isolation and duplicate declaration rejection.
- Strict type-checking across binary expressions ($+, -, *, /, \%, ==, !=, <, >, <=, >=, \&\&, ||$).
- Mandatory return paths on all control-flow trajectories for non-void functions.
- Bounds enforcement restricting integer literals strictly to $[-2^{31}, 2^{31}-1]$.

## 3.3 Bytecode ISA and Binary File Format
VeriByte targets a compact 27-opcode stack ISA:

| Category | Opcodes | Operand / Stack Transition |
|:---|:---|:---|
| Stack Manipulation | `PUSH_INT` $k$ | $\epsilon \to [\text{int}]$ (4-byte immediate) |
| | `PUSH_BOOL` $b$ | $\epsilon \to [\text{bool}]$ (1-byte immediate) |
| | `POP` | $[T] \to \epsilon$ |
| | `DUP` | $[T] \to [T, T]$ |
| Arithmetic (i32) | `ADD`, `SUB`, `MUL` | $[\text{int}, \text{int}] \to [\text{int}]$ |
| | `DIV`, `MOD` | $[\text{int}, \text{int}] \to [\text{int}]$ (traps on 0) |
| | `NEG` | $[\text{int}] \to [\text{int}]$ |
| Logic & Compare | `AND`, `OR` | $[\text{bool}, \text{bool}] \to [\text{bool}]$ |
| | `NOT` | $[\text{bool}] \to [\text{bool}]$ |
| | `EQ`, `NE` | $[T, T] \to [\text{bool}]$ (types must match) |
| | `LT`, `GT`, `LE`, `GE` | $[\text{int}, \text{int}] \to [\text{bool}]$ |
| Local Variables | `LOAD` $i$ | $\epsilon \to [T_i]$ (2-byte index) |
| | `STORE` $i$ | $[T_i] \to \epsilon$ (2-byte index) |
| Control Flow | `JMP` $addr$ | $\epsilon \to \epsilon$ (2-byte target offset) |
| | `JMP_IF_FALSE` $addr$ | $[\text{bool}] \to \epsilon$ (2-byte target offset) |
| Functions & I/O | `CALL` $f$ | $[T_1, \dots, T_k] \to [T_{ret}]$ (2-byte fn) |
| | `RET` | $[T_{ret}] \to \text{caller stack}$ |
| | `PRINT` | $[T] \to \epsilon$ |
| | `HALT` | $[T] \to \text{exit}$ |

The serialized binary format (`.bc`) consists of an immutable header:
1. **Magic Number & Version:** 4-byte ASCII `SBVM` followed by a 2-byte little-endian version code (`0x0001`).
2. **Function Table Header:** 2-byte function count and 2-byte entry function index.
3. **Function Descriptors:** Per function: name, parameter count, parameter types, return type, local slot count, local types, declared `max_stack`, code length, and raw code bytes.

## 3.4 Static Bytecode Verifier (Core Contribution)
The static verifier is constructed as an abstract interpreter operating over a monotone dataflow framework. For each function $F$, the verifier models state:
$$\sigma \in \Sigma = \text{StackType}^* \times \text{LocalType}^M$$
where $\text{StackType} \in \{\text{int}, \text{bool}\}$ and $\text{LocalType} \in \{\text{int}, \text{bool}, \text{UNSET}, \text{CONFLICT}\}$.

The verification algorithm proceeds in five sequential phases:

### Phase 1: Module Header Validation
The module header is verified to guarantee structural consistency:
- The module contains at least one function ($|F| \ge 1$).
- The entry function index references a valid function named `main` taking zero parameters and returning `int`.
- For every function, $\text{len}(\text{local\_types}) = \text{num\_locals}$, $\text{num\_locals} \ge \text{num\_params}$, and the prefix of $\text{local\_types}$ precisely matches $\text{param\_types}$.

### Phase 2: Linear Instruction Decoding
The function byte stream is decoded sequentially. The verifier checks that every opcode is valid, operands do not truncate beyond code boundaries, and `PUSH_BOOL` immediates are strictly `0x00` or `0x01`. The offset of every instruction boundary is recorded into an interval set $\mathcal{I}_{starts}$.

### Phase 3: Control-Flow Graph & Jump Boundary Verification
For every control-flow transfer instruction (`JMP`, `JMP_IF_FALSE`), the target address $A_{target}$ is validated against $\mathcal{I}_{starts}$:
$$A_{target} \in \mathcal{I}_{starts} \quad \land \quad 0 \le A_{target} < \text{len}(\text{code})$$
Jumps landing mid-instruction or exceeding function code bounds are rejected immediately with `BAD_JUMP`.

### Phase 4: Worklist Abstract Interpretation
Verification initializes a double-ended worklist queue $\mathcal{W}$ with entry offset 0. The entry abstract state $\sigma_0$ is defined as:
$$\sigma_0 = \langle \text{stack} = [], \text{locals} = [T_1, \dots, T_k, \text{UNSET}, \dots, \text{UNSET}] \rangle$$
where parameters $T_1 \dots T_k$ are typed, and all local variables allocated beyond parameters are marked `UNSET`.

For each instruction popped from $\mathcal{W}$, the verifier evaluates preconditions, computes the transfer function $\tau(op, \sigma) \to \sigma'$, and merges $\sigma'$ into the states of its control-flow successors.

### Phase 5: Join-Point Merging and Definite Assignment
When multiple control-flow paths merge at offset $j$, the incoming state $\sigma_{in}$ is merged with the existing state $\sigma_{j}$ according to the confluence operator $\sqcap$:
$$\text{depth}(\sigma_{in}.\text{stack}) = \text{depth}(\sigma_j.\text{stack}) \quad (\text{else } \texttt{MERGE\_MISMATCH})$$
$$\sigma_j.\text{stack}[k] = \sigma_{in}.\text{stack}[k] \quad (\text{else } \texttt{MERGE\_MISMATCH})$$
$$\sigma_j.\text{locals}[i] = \begin{cases}
T & \text{if } \sigma_{in}.\text{locals}[i] = \sigma_j.\text{locals}[i] = T \\
\text{UNSET} & \text{if either is } \text{UNSET} \\
\text{CONFLICT} & \text{otherwise}
\end{cases}$$
If local $i$ is not initialized along all convergent execution trajectories, it resolves to `UNSET`. Any subsequent `LOAD` $i$ instruction encountering an `UNSET` state is rejected with `LOCAL_UNSET`.

### The Thirteen Invariant Rules

| Rule Name | Violation Condition & Security Rationale |
|:---|:---|
| `BAD_OPCODE` | Undefined byte value or invalid boolean immediate. |
| `TRUNCATED` | Byte stream terminates before reading immediate operand. |
| `BAD_JUMP` | Jump target is out of bounds or lands mid-instruction. |
| `STACK_UNDERFLOW` | Popping when stack depth is insufficient for opcode. |
| `STACK_OVERFLOW` | Pushing when stack depth equals declared `max_stack`. |
| `STACK_TYPE` | Operand type does not match required instruction type. |
| `MERGE_MISMATCH` | Converging branches have different stack depths or types. |
| `LOCAL_RANGE` | Accessing local index $\ge \text{num\_locals}$. |
| `LOCAL_TYPE` | Storing an operand incompatible with declared local type. |
| `LOCAL_UNSET` | Reading a local variable before definite assignment. |
| `BAD_CALL` | Callee index invalid or argument types mismatch signature. |
| `BAD_RETURN` | Stack depth $\ne 1$ or top value mismatches function return type. |
| `FALLTHROUGH` | Instruction flow runs off end of code without `RET`/`HALT`. |

## 3.5 Virtual Machine Interpreter & Checked Soundness Oracle
The virtual machine executes verified bytecode through an activation-frame stack. Each call frame allocates an isolated local variable array and an operand stack. Arithmetic instructions evaluate over 32-bit two's complement representation:
$$\text{to\_i32}(v) = (v + 2^{31} \pmod{2^{32}}) - 2^{31}$$
Division or modulo by zero raises a clean, recoverable `VMTrap("division by zero")` without crashing the host process. Call depth recursion is bounded at 10,000 frames to prevent host stack exhaustion.

To validate soundness during fuzzing, the VM incorporates a **Checked Mode** (`checked=True`). In checked mode, the VM validates hardware-level safety invariants at every cycle:
1. Arithmetic/comparison operands must satisfy $\text{type}(v) \equiv \text{int}$.
2. Logical and conditional branch operands must satisfy $\text{type}(v) \equiv \text{bool}$.
3. `EQ`/`NE` operands must have identical concrete types.
4. `LOAD` must not yield `None` (confirming definite assignment).
5. `STORE` must match declared slot types.
6. Stack depth after any push must not exceed declared `max_stack`.
7. `RET` must leave exactly one value matching function return type.
8. Program counter must remain within valid instruction start boundaries.

Any invariant violation in checked mode raises `VMInvariantError`, flagging a soundness defect in the static verifier.

## 3.6 Bytecode Optimization Pipeline
The bytecode optimizer lifts raw bytecode into an Intermediate Representation (IR) consisting of explicit basic blocks. Optimization passes include:
- **Constant Folding:** Algebraic reduction of constant arithmetic and comparison operations (e.g., $10 + 20 \to 30$).
- **Dead Instruction Elimination:** Removal of redundant `PUSH` followed immediately by `POP`, and double logical negation (`NOT NOT`).
- **Jump Threading:** Elimination of jumps pointing to the immediate subsequent instruction offset.
- **Unreachable Code Elimination:** Dead block pruning following unconditional returns or jumps.

Crucially, VeriByte enforces verified optimization: the pipeline verifies the input bytecode, executes optimization passes, recalculates jump targets and stack limits, and re-verifies the optimized bytecode prior to execution.

# 4. Results and Discussion

The experimental evaluation of VeriByte investigates five empirical research questions:
- **RQ1 (Precision):** Does the verifier accept all valid compiled programs with zero false rejections?
- **RQ2 (Attack Rejection):** Does the verifier accurately detect and isolate each of the 13 safety violations?
- **RQ3 (Soundness):** Across random differential fuzzing, do accepted mutants execute without invariant violations?
- **RQ4 (Loader Hardening):** How robust is binary deserialization against raw bit flips?
- **RQ5 (Performance):** What is the computational overhead and scaling factor of load-time verification?

## 4.1 Unit Test Suite and Precision (RQ1)
The regression test suite consists of 195 automated tests executing via the standard library test runner. The test suite covers:
- Front-end lexing and parsing: 22 tests.
- Semantic type analysis and bounds checking: 56 tests.
- Code generation, serialization, and disassembly: 13 tests.
- Virtual machine execution and wraparound arithmetic: 18 tests.
- Static verifier rule isolation: 38 tests.
- Disk-based malicious binary suite: 1 test (26 subtests).
- Bytecode optimizer equivalence: 13 tests.
- Malformed binary and literal hardening: 7 tests.
- Checked-mode soundness invariants and oracle meta-tests: 27 tests.

All 195 tests pass with zero failures or errors. Across all canonical example programs (`factorial.ml`, `fibonacci.ml`, `gcd.ml`, `logic.ml`, `prime.ml`), verification achieved a **0% false-rejection rate** both before and after bytecode optimization.

## 4.2 Handcrafted Exploit Corpus Validation (RQ2)

Under verified mode, **100% of the malicious binaries were cleanly intercepted and rejected** with precise diagnostic error messages detailing the function name, instruction offset, mnemonic, violated rule, and stack state.

## 4.3 Differential Mutation Fuzzing (RQ3)
We executed a campaign of 15,000 mutants across the 5 canonical seed programs over three independent random seeds (101, 202, 303), testing 1,000 mutations per program per seed with bytecode optimization (`--opt`) and active VM checked mode.

| Unsafe Mode Crashes  | 3,154 | 3,144 | 3,123 | **9,421 (77.0%)** |

The rejection distribution across the 12,231 rejected mutants exercised all 13 safety rules:
- `BAD_OPCODE`: 5,402 (44.2%)
- `LOCAL_RANGE`: 1,449 (11.8%)
- `BAD_CALL`: 1,200 (9.8%)
- `TRUNCATED`: 1,144 (9.4%)
- `BAD_JUMP`: 667 (5.5%)
- `FALLTHROUGH`: 632 (5.2%)

- `STACK_UNDERFLOW`: 397 (3.2%)

Crucially, across all 2,769 accepted mutants executed in checked mode, **zero soundness violations occurred**. 2,528 programs ran to clean completion, 43 terminated safely via expected division-by-zero traps (`VMTrap`), and 198 safely terminated via step-limit timeouts. When rejected mutants were executed in unverified mode, **9,421 crashed with unhandled host exceptions**, demonstrating that the verifier successfully prevented thousands of potential runtime faults.

## 4.4 Raw-Byte Serializer Hardening Fuzzing (RQ4)
To evaluate whether corrupted binary files could trigger unhandled exceptions in the binary loader, we executed the fuzzer in file-level mode (`--file-mode`), mutating raw serialized `.bc` bytes directly across 10,000 mutants (Seeds 101 and 202).

| Outcome | Seed 101 | Seed 202 | Combined |
|:---|:---|:---|:---|
| Total Mutated Files | 5,000 | 5,000 | 10,000 |
| Loader Rejections (`FORMAT_ERROR`) | 2,787 (55.7%) | 2,791 (55.8%) | 5,578 (55.8%) |
| Verifier Rejections (`VerifyError`) | 1,592 (31.8%) | 1,570 (31.4%) | 3,162 (31.6%) |
| Accepted Files | 621 (12.4%) | 639 (12.8%) | 1,260 (12.6%) |
| **Soundness Violations** | **0** | **0** | **0 (Zero)** |

Across 10,000 raw corrupted files, exactly 5,578 were intercepted by the hardened binary loader with clean `BytecodeFormatError` exceptions, and 3,162 passed the loader but were rejected by the static verifier. Zero unhandled Python exceptions escaped, demonstrating complete defensive encapsulation of the binary ingestion boundary.

## 4.5 Validating the Soundness Oracle (Meta-Test)
A potential threat to validity in fuzzing campaigns is a vacuous oracle—an oracle that never reports a failure because its internal invariant assertions are disabled. To validate our oracle's sensitivity, we implemented an automated meta-test in `tests/test_oracle.py`.

The test temporarily disables the verifier's operand-type check specifically for `Op.ADD` (`CHECK_STACK_TYPE_ADD = False`) and synthesizes a program pushing a boolean and an integer before executing `ADD`. The weakened verifier improperly accepts the binary. Upon admission to the checked VM, the runtime oracle immediately detects the non-integer operand and raises `VMInvariantError`, recording a soundness violation. This meta-test confirms that the checked VM oracle reliably identifies real verifier omissions.

## 4.6 Performance Benchmarks and Scaling (RQ5)
Verification performance was profiled across synthetic programs of increasing size (up to 1,000 statements / 12,012 bytecode bytes):
- **252 Bytes (20 statements):** $\approx 1.4\text{ ms}$ ($176\text{ KB/s}$)
- **612 Bytes (50 statements):** $\approx 3.0\text{ ms}$ ($198\text{ KB/s}$)
- **1,212 Bytes (100 statements):** $\approx 7.1\text{ ms}$ ($167\text{ KB/s}$)
- **3,012 Bytes (250 statements):** $\approx 15.9\text{ ms}$ ($185\text{ KB/s}$)
- **6,012 Bytes (500 statements):** $\approx 31.2\text{ ms}$ ($188\text{ KB/s}$)
- **12,012 Bytes (1,000 statements):** $\approx 66.3\text{ ms}$ ($177\text{ KB/s}$)

Throughput remained steady at approximately $180\text{ KB/s}$ across all workloads. When evaluated against total application execution time across realistic benchmarks (`factorial`, `fibonacci`, `gcd`, `prime`), static verification accounted for **less than 0.5% of runtime execution latency** (and under 0.1% for compute-heavy recursive workloads). Bytecode optimization yielded up to **28.9% bytecode size reduction** and up to **1.28x execution speedup** on constant-heavy routines.

# 5. Conclusions and Future Work

This paper presented VeriByte, a secure bytecode compilation, verification, and execution toolchain. By elevating the compiler and virtual machine loader into a formal trust boundary, VeriByte guarantees that untrusted bytecode cannot induce stack underflows, type confusion, invalid control-flow transfers, or uninitialized memory reads.

Through abstract interpretation over a monotone type lattice, VeriByte enforces thirteen structural and behavioral safety rules. Across 195 unit tests, 26 handcrafted exploit binaries, 15,000 structural mutants, and 10,000 raw binary byte mutations, the static verifier achieved zero false rejections on valid programs, intercepted over 9,400 unhandled execution crashes, and recorded zero soundness violations under active runtime oracle checking. With strictly linear $O(N)$ scaling and an execution overhead below 0.5%, VeriByte demonstrates that static verification provides robust, cost-effective security for intermediate code execution.

## 5.1 Future Work
Future research directions include:
1. **Array and Heap Allocation Bounds:** Extending the type system and verifier to support fixed-size arrays with static index analysis and provably safe heap references.
2. **Stack Map Tables:** Transitioning from full worklist abstract interpretation to single-pass linear verification via compiler-generated stack map tables, mirroring modern Java 6+ class file verification.
3. **Short-Circuit Logic Evaluation:** Extending the code generator and AST lowering to support short-circuit boolean semantics for `&&` and `||`.
4. **Formal Machine-Checked Soundness Proofs:** Formalizing the operational semantics and progress-preservation theorems in interactive theorem provers such as Coq or Lean.
5. **Just-In-Time (JIT) Compilation:** Integrating a native JIT compiler (targeting x86-64 or ARM64) that directly compiles verified bytecode with eliminated runtime safety checks.
