# Paper Title: VeriByte: Design, Formalization, and Empirical Soundness Evaluation of a Secure Bytecode Virtual Machine with Static Dataflow Verification

**Authors**: Dhyanam M. N., Faculty Advisor / Guide  
**Department**: Department of Computer Science and Engineering, School of Engineering and Technology  

---

## 1. ABSTRACT
Virtual machines executing intermediate bytecode representations—exemplified by the Java Virtual Machine (JVM), WebAssembly (Wasm) runtimes, and Linux extended Berkeley Packet Filters (eBPF)—form foundational infrastructure for sandboxed and portable code execution. However, when bytecode originates from untrusted compilers, malicious adversaries, or corrupted transport channels, direct execution induces fatal vulnerabilities including stack underflow/overflow, type confusion, out-of-bounds local access, and control-flow hijacking. Traditional sandboxing mitigates these threats through continuous runtime boundary checks, introducing substantial instruction dispatch overhead (often 200%–500%).

This paper introduces **VeriByte**, an end-to-end secure programming language toolchain and stack-based virtual machine governed by an ahead-of-time static bytecode verifier based on abstract interpretation. The verifier models program execution over an abstract domain of typed symbolic operand stacks and definitely assigned variable frames across a monotone dataflow framework. We formalize thirteen comprehensive safety rules encompassing control-flow validity, operand-type safety, frame convergence, definite assignment, and call/return isolation. We demonstrate an attack-and-defence paradigm across 26 handcrafted exploit binaries and evaluate empirical soundness via differential mutation fuzzing across 15,000 structural mutants and 10,000 raw-byte corrupted binaries under an active runtime checking oracle. Over 25,000 stress inputs, the verifier exhibited zero false rejections on valid programs and zero soundness violations across all accepted binaries, while preventing 9,421 catastrophic unhandled crashes. Load-time verification imposes strictly linear $\mathcal{O}(N)$ scaling with an overhead below 0.5% of execution time.

**Keywords**: Bytecode Verification, Abstract Interpretation, Type Safety, Virtual Machine, Static Dataflow Analysis, Soundness Oracle, Differential Fuzzing.

## 2. INTRODUCTION
Modern software deployment relies heavily on platform-independent bytecode architectures. Compiling source code into an intermediate bytecode distributed to a client-side or in-kernel virtual machine (VM) decouples language implementations from hardware targets while theoretically establishing a sandboxed isolation boundary. Representative architectures span the Java Virtual Machine, the Common Language Runtime (CLR), browser-embedded WebAssembly engines, and kernel-space eBPF execution engines.

In standard compiler curricula and baseline runtime engines, compiler design ends at syntax-directed code generation, leaving the execution engine to implicitly trust the generated bytecode. In adversarial environments, this implicit trust model fails catastrophically. A binary executable can be hand-crafted in binary hex editors, emitted by compromised third-party compilers, or corrupted during network transit. When an untrusted bytecode binary containing invalid control-flow targets or mismatched stack operands enters a native VM loop, it triggers:
1. **Stack Underflow and Overflow:** Popping from an empty evaluation stack reads adjacent host memory; pushing beyond capacity corrupts activation frames.
2. **Control-Flow Hijacking:** Jump targets pointing into the middle of multi-byte instruction encodings cause data operands to be decoded as opcodes, leading to arbitrary code execution.
3. **Type Confusion:** Arithmetic instructions executing against boolean flags or object references bypass high-level type safety invariants.
4. **Uninitialized Local Access:** Reading unassigned local variable slots leaks unscrubbed host memory registers.

To counter these vulnerabilities without paying the steep runtime performance penalty of defensive interpreter traps (which require checking stack pointers and dynamic types at every fetch-decode-execute step), modern architectures enforce static bytecode verification prior to program instantiation.

In this work, we present **VeriByte**, a complete, fully verifiable stack-based compilation and execution pipeline designed as a trust boundary. VeriByte implements an imperative source language (*MiniLang*), a two-pass semantic type analyzer, a 27-opcode stack-based binary bytecode generator, a bytecode optimizer with constant folding and jump threading, a static bytecode verifier employing Kildall's worklist abstract interpretation algorithm, and a high-performance virtual machine interpreter equipped with a checked-mode verification oracle.

The primary contributions of this paper are:
- **System Architecture as a Security Boundary:** We establish an end-to-end verifiable pipeline enforcing the principle that no untrusted bytecode is ever admitted to the runtime interpreter without preceding inductive safety verification.
- **Thirteen Formalized Safety Rules:** We formalize and implement thirteen static safety invariants spanning bytecode structure, control-flow graphs (CFGs), operand-type lattices, join-point stack unification, and call/return typing.
- **Attack-and-Defence Corpus:** We validate verifier precision against a handcrafted corpus of 26 exploit binaries designed to isolate each rule violation, juxtaposing unverified execution crashes against clean verifier rejections.
- **Checked Soundness Oracle and Differential Fuzzing:** We evaluate verifier soundness via a 15,000-mutant structural fuzzing campaign and a 10,000-mutant raw-byte serializer fuzzing campaign. We validate the fuzzer's sensitivity through an intentional verifier weakening meta-test.
- **Empirical Performance Profiling:** We demonstrate that verification scales linearly ($\approx 180\text{ KB/s}$) with an execution overhead under 0.5%, confirming the practical viability of load-time verification.

## 3. LITERATURE SURVEY
The theoretical foundations of static bytecode verification originate in abstract interpretation, type systems, and monotone dataflow frameworks.

### A. JVM Bytecode Verification and Stack Maps
Early iterations of the Java Virtual Machine Specification implemented dataflow-based type inference to reconstruct operand stack shapes at runtime. In seminal work, Leroy formalized Java bytecode verification using abstract interpretation over an abstract machine, establishing proof obligations for type safety and progress-preservation properties. However, because multi-path type inference exhibits polynomial computational complexity, Sun Microsystems introduced the `StackMapTable` attribute in Java ME and Java 6+. Rather than inferring types from scratch, the modern JVM validator verifies pre-computed type annotations in linear time. VeriByte deliberately adopts the more academically rich full-inference abstract interpretation approach, solving the fixpoint over loop back-edges without requiring external compiler-assisted stack maps.

### B. WebAssembly Validation
WebAssembly (Wasm) was designed specifically to provide memory-safe, near-native execution inside web browsers. Unlike arbitrary stack machines, Wasm enforces structured control flow (avoiding arbitrary goto/jump instructions). This enables single-pass linear validation where operand stacks are validated syntactically using typed block signatures. While structured control flow simplifies validation, legacy and low-level architectures rely on unstructured jump primitives. VeriByte tackles the more generalized, unstructured control-flow domain where jumps can target arbitrary byte offsets, necessitating explicit CFG decoding and merge reconciliation.

### C. Linux Kernel eBPF Verification
Extended Berkeley Packet Filters (eBPF) permit user-space applications to execute sandboxed code inside the Linux kernel. Because kernel panics are unacceptable, the kernel's in-tree verifier performs symbolic execution to simulate all possible execution paths, validating that registers contain safe data types, pointer arithmetic stays within allocated buffer boundaries, and programs terminate within bounded instruction limits. VeriByte adopts a comparable threat model: untrusted binaries submitted from external sources must pass static analysis before admission to the runtime.

### D. Abstract Interpretation Foundations
Cousot and Cousot established abstract interpretation as a unified lattice model for approximating the semantics of programming languages. In VeriByte, the concrete execution domain (holding 32-bit integer values and boolean bits) is abstracted into a finite type lattice ($\mathbb{L} = \{\bot, \text{int}, \text{bool}, \top\}$), augmented with definite assignment tracking states ($\{\text{UNSET}, \text{CONFLICT}\}$). Monotonicity over this bounded-height lattice guarantees convergence to a fixed point.

## 4. METHODOLOGY AND ARCHITECTURE

### A. System Architecture
The VeriByte toolchain is organized into modular phases forming an end-to-end compiler and verification boundary:
- **Source Compilation Pipeline:** Source files (`.ml`) pass through lexical analysis, recursive-descent parsing with precedence climbing, two-pass semantic type analysis, stack bytecode generation, and optional optimization before entering the verifier and VM.
- **Bytecode Admission Pipeline:** Externally supplied or precompiled bytecode files (`.bc`) enter directly at the serializer loader. The loader decodes header tables and immediately invokes the static verifier. Only bytecode certified as safe is permitted to initialize the virtual machine execution frames.

### B. Source Language (MiniLang)
MiniLang is a strongly typed imperative language supporting 32-bit signed integers and booleans. Its syntax includes variable declarations (`let`), lexical block scopes, conditional branches (`if` / `else if` / `else`), iterative loops (`while`), first-class function declarations with explicit signatures, return statements, and console printing (`print`).

The semantic analyzer enforces:
- Lexical scope isolation and duplicate declaration rejection.
- Strict type-checking across binary expressions ($+, -, *, /, \%, ==, !=, <, >, <=, >=, \&\&, ||$).
- Mandatory return paths on all control-flow trajectories for non-void functions.
- Bounds enforcement restricting integer literals strictly to $[-2^{31}, 2^{31}-1]$.

### C. Bytecode ISA and Binary File Format
VeriByte targets a compact 27-opcode stack ISA:
- **Stack Manipulation:** `PUSH_INT` $k$, `PUSH_BOOL` $b$, `POP`, `DUP`.
- **Arithmetic (i32):** `ADD`, `SUB`, `MUL`, `DIV`, `MOD`, `NEG`.
- **Logic & Compare:** `AND`, `OR`, `NOT`, `EQ`, `NE`, `LT`, `GT`, `LE`, `GE`.
- **Local Variables:** `LOAD` $i$, `STORE` $i$.
- **Control Flow:** `JMP` $addr$, `JMP_IF_FALSE` $addr$.
- **Functions & I/O:** `CALL` $f$, `RET`, `PRINT`, `HALT`.

The serialized binary format (`.bc`) consists of an immutable header:
1. **Magic Number & Version:** 4-byte ASCII `SBVM` followed by a 2-byte little-endian version code (`0x0001`).
2. **Function Table Header:** 2-byte function count and 2-byte entry function index.
3. **Function Descriptors:** Name, parameter count, parameter types, return type, local count, local types, declared `max_stack`, code length, and raw code.

### D. Static Bytecode Verifier (Core Contribution)
The static verifier is constructed as an abstract interpreter operating over a monotone dataflow framework:
$$\sigma \in \Sigma = \text{StackType}^* \times \text{LocalType}^M$$
where $\text{StackType} \in \{\text{int}, \text{bool}\}$ and $\text{LocalType} \in \{\text{int}, \text{bool}, \text{UNSET}, \text{CONFLICT}\}$.

The verification algorithm proceeds in five sequential phases:
1. **Module Header Validation:** Confirms valid function count, valid entry function (`main(): int` taking 0 parameters), local count $\ge$ parameter count, and parameter types matching the initial local types prefix.
2. **Linear Instruction Decoding:** Disassembles the byte stream sequentially, checks for unknown opcodes, checks for truncated immediates, asserts boolean immediates are $0$ or $1$, and records all valid instruction start offsets into $\mathcal{I}_{starts}$.
3. **CFG & Jump Target Validation:** Ensures every target offset in `JMP` and `JMP_IF_FALSE` exists in $\mathcal{I}_{starts}$ and is strictly within function bounds.
4. **Worklist Abstract Interpretation:** Evaluates instructions iteratively via a worklist queue $\mathcal{W}$, applying abstract transfer functions $\tau(op, \sigma) \to \sigma'$.
5. **Join-Point Merging & Definite Assignment:** At control-flow merge points, stack depths must match exactly and slot types must match identical types, otherwise `MERGE_MISMATCH` is triggered. Unassigned locals merge to `UNSET`; any subsequent `LOAD` of an `UNSET` variable is rejected as `LOCAL_UNSET`.

The verifier strictly enforces thirteen rules:
- `BAD_OPCODE`, `TRUNCATED`, `BAD_JUMP`, `STACK_UNDERFLOW`, `STACK_OVERFLOW`, `STACK_TYPE`, `MERGE_MISMATCH`, `LOCAL_RANGE`, `LOCAL_TYPE`, `LOCAL_UNSET`, `BAD_CALL`, `BAD_RETURN`, `FALLTHROUGH`.

### E. Virtual Machine Interpreter & Checked Soundness Oracle
The VM interpreter executes verified bytecode through an activation-frame stack. Each call frame allocates an isolated local variable array and an operand stack. Arithmetic instructions evaluate over 32-bit two's complement representation. Division or modulo by zero raises a clean, recoverable `VMTrap("division by zero")` without crashing the host process. Call depth recursion is bounded at 10,000 frames to prevent host stack exhaustion.

In **Checked Mode** (`checked=True`), the VM validates hardware-level safety invariants at every cycle (types, stack limits, definite assignment, bounds, return shape). Any violation raises `VMInvariantError`, exposing verifier soundness defects during fuzzing.

### F. Bytecode Optimization Pipeline
The optimizer lifts raw bytecode into an Intermediate Representation (IR) consisting of explicit basic blocks. Optimization passes include constant folding, dead instruction elimination (`PUSH` then `POP`, `NOT NOT`), jump threading, and unreachable code elimination. The pipeline enforces verified optimization: the bytecode is verified before and after optimization to guarantee semantics and safety preservation.

## 5. RESULTS AND DISCUSSION

### A. Unit Test Suite and Precision (RQ1)
The test suite consists of 195 automated tests executing via the standard library test runner:
- Front-end lexing & parsing: 22 tests.
- Semantic type analysis & bounds checking: 56 tests.
- Code generation, serialization & disassembly: 13 tests.
- VM execution & wraparound arithmetic: 18 tests.
- Static verifier rule isolation: 38 tests.
- Malicious exploit files on disk: 1 test (26 subtests).
- Bytecode optimizer equivalence: 13 tests.
- Malformed binary & literal hardening: 7 tests.
- Soundness oracle invariants & meta-test: 27 tests.

All 195 tests pass with zero failures or errors. Verification achieved a **0% false-rejection rate** on all valid example programs both before and after bytecode optimization.

### B. Handcrafted Exploit Corpus Validation (RQ2)
To evaluate rule precision, 26 malicious bytecode files (two per safety rule) were evaluated. Under unverified execution (`--unsafe`), 22 of 26 files crashed catastrophically with unhandled host exceptions (`IndexError: pop from empty list`, `IndexError: list index out of range`), while the remaining 4 produced severe type confusion or memory overconsumption. Under verified mode, **100% of malicious files were cleanly rejected** with diagnostic error messages.

### C. Differential Mutation Fuzzing (RQ3)
We executed a campaign of 15,000 mutants across the 5 canonical seed programs over three independent random seeds (101, 202, 303), testing 1,000 mutations per program per seed with bytecode optimization (`--opt`) and active VM checked mode:
- **Total Mutants Tested**: 15,000
- **Accepted by Verifier**: 2,769 (18.5%)
- **Rejected by Verifier**: 12,231 (81.5%)
- **Unsafe Mode VM Crashes**: 9,421 (77.0% of rejections)
- **Soundness Violations**: **0 (Zero)**

Across all 2,769 accepted mutants executed in checked mode, **zero soundness violations occurred** (2,528 ran to completion, 43 ended in division-by-zero `VMTrap`, 198 reached step limits). Over 9,421 unverified mutants crashed with unhandled exceptions in unsafe mode, confirming that the verifier effectively prevented thousands of runtime faults.

### D. Raw-Byte Serializer Hardening Fuzzing (RQ4)
To evaluate binary loader robustness against bit corruptions, the fuzzer was run in file-level mode (`--file-mode`) across 10,000 raw mutants (Seeds 101 and 202):
- **Total Mutated Files**: 10,000
- **Loader Rejections (`FORMAT_ERROR`)**: 5,578 (55.8%)
- **Verifier Rejections (`VerifyError`)**: 3,162 (31.6%)
- **Accepted Files**: 1,260 (12.6%)
- **Soundness Violations**: **0 (Zero)**

Zero unhandled Python exceptions escaped during binary ingestion, validating complete defensive encapsulation of the file loader.

### E. Validating the Soundness Oracle (Meta-Test)
To confirm the fuzzer oracle is not vacuous, an automated meta-test temporarily disables the verifier's operand-type check for `Op.ADD` (`CHECK_STACK_TYPE_ADD = False`). The weakened verifier improperly accepts a program adding a boolean and an integer. When admitted to the checked VM, the runtime oracle immediately detects the non-integer operand and raises `VMInvariantError`, proving that the checked VM oracle reliably identifies real verifier omissions.

### F. Performance Benchmarks and Scaling (RQ5)
Verification scaling was profiled on synthetic programs up to 12,012 bytes:
- 252 Bytes (20 statements): $\approx 1.4\text{ ms}$ ($176\text{ KB/s}$)
- 1,212 Bytes (100 statements): $\approx 7.1\text{ ms}$ ($167\text{ KB/s}$)
- 6,012 Bytes (500 statements): $\approx 31.2\text{ ms}$ ($188\text{ KB/s}$)
- 12,012 Bytes (1,000 statements): $\approx 66.3\text{ ms}$ ($177\text{ KB/s}$)

Verification latency scaled strictly linearly $\mathcal{O}(N)$. Static verification accounted for **less than 0.5% of runtime execution latency** across realistic benchmarks, while bytecode optimization yielded up to **28.9% code size reduction** and up to **1.28x speedup**.

## 6. CONCLUSIONS AND FUTURE WORK
This paper presented VeriByte, a secure bytecode compilation, verification, and execution toolchain. By elevating the compiler and virtual machine loader into a formal trust boundary, VeriByte guarantees that untrusted bytecode cannot induce stack underflows, type confusion, invalid control-flow transfers, or uninitialized memory reads.

Through abstract interpretation over a monotone type lattice, VeriByte enforces thirteen structural and behavioral safety rules. Across 195 unit tests, 26 handcrafted exploit binaries, 15,000 structural mutants, and 10,000 raw binary byte mutations, the static verifier achieved zero false rejections on valid programs, intercepted over 9,400 unhandled execution crashes, and recorded zero soundness violations under active runtime oracle checking. With strictly linear $\mathcal{O}(N)$ scaling and an execution overhead below 0.5%, VeriByte demonstrates that static verification provides robust, cost-effective security for intermediate code execution.

### Future Work
Future research directions include:
1. **Array and Heap Allocation Bounds:** Extending the type system and verifier to support fixed-size arrays with static index analysis and provably safe heap references.
2. **Stack Map Tables:** Transitioning from full worklist abstract interpretation to single-pass linear verification via compiler-generated stack map tables, mirroring modern Java 6+ class file verification.
3. **Short-Circuit Logic Evaluation:** Extending the code generator and AST lowering to support short-circuit boolean semantics for `&&` and `||`.
4. **Formal Machine-Checked Soundness Proofs:** Formalizing the operational semantics and progress-preservation theorems in interactive theorem provers such as Coq or Lean.
5. **Just-In-Time (JIT) Compilation:** Integrating a native JIT compiler (targeting x86-64 or ARM64) that directly compiles verified bytecode with eliminated runtime safety checks.
